01

What's already real

Not this doc's subject, but the ground everything below stands on — verify it before trusting anything after this section.

apps/api/src/modules/payments (20 Aug 2026, hardened 25 Aug 2026) is a genuine order/verify/webhook flow shared by Subscribe (§M) and Program Purchase (§I): POST /payments/razorpay/orders resolves the real server-side price and creates a Razorpay Order; POST /payments/razorpay/verify recomputes the HMAC signature with a timing-safe comparison — the actual security boundary, never the client's say-so; POST /payments/razorpay/webhook is an independent second path to the same idempotent activatePayment(), so a client crash after a real charge still ends in a granted purchase. A Payment reaching paid auto-generates one real Invoice (Module 10 Finance). Admin has a real, read-only Payments Directory + Transaction Detail (06.02/06.03) and a real Integrations-screen status tile for the gateway. A boot-time guard already refuses to start with a live Razorpay key unless PRICE_CURRENCY_CONFIRMED=true — see §02, this is the safety net for the decision below, not the decision itself. None of this needed re-verifying for this pass; re-confirmed by direct read of payments.service.ts, razorpayClient.ts, payments.routes.ts, subscriptions.service.ts, programPurchases.service.ts, adminPayments.service.ts, and config/env.ts for this doc.

02

The one decision that blocks real money moving at all

A pricing call, not an engineering one — laid out here, not made here. Nothing else in this plan matters until this is resolved.

The problem

Every seeded SubscriptionPlan/Program priceCents value was chosen and is displayed as USD cents (Pro plan priceCents=1499 renders as $14.99 on SubscriptionScreen.tsx). Razorpay's native currency is INR, and RAZORPAY_CURRENCY defaults to "INR". Passing 1499 straight through as paisa charges ₹14.99 — real ~₹1,200 worth of product for about 1.2¢ on the dollar, roughly an 80x undercharge on every single transaction.

Status

Not decided. config/env.ts refuses to boot with a live key (rzp_live_...) unless PRICE_CURRENCY_CONFIRMED=true is explicitly set — so this can't fail silently in production — but that guard is a seatbelt, not a steering decision. Test keys (rzp_test_...) boot freely today, so the full flow is already exercisable end to end in test mode without this being resolved first.

The two real options
  1. Reprice everything in real INR. Replace every seeded priceCents with an actual India-market list price (paisa), and change every price-displaying screen's currency formatting from $X.XX to ₹X — SubscriptionScreen.tsx, ProgramDetailScreen.tsx, WorkoutDetailScreen.tsx, plus every admin Commerce/Finance screen that renders amountCents. A content/pricing task (real numbers to choose), not a hard engineering one.
  2. Keep USD list prices, settle in USD. Configure a Razorpay account for international/USD settlement and set RAZORPAY_CURRENCY=USD — no seed-data or screen changes needed, but this is a Razorpay account-configuration and compliance question (international settlement isn't every merchant account's default), not something this build can verify from here.

Either is genuinely buildable. Neither is a call this pass can make on your behalf — see this session's standing caution around money-movement functionality.

Once decided

Set PRICE_CURRENCY_CONFIRMED=true only after one of the two options above is actually implemented, get real (even just test-mode) Razorpay credentials into .env — see §04's callout — and the core flow in §01 is ready for real transactions.

Full inventory — 14 items

Every pending or partial piece of the Payments/Commerce surface found by direct inspection, ordered by what unlocks the most next. Tag color is the same convention as build-plan.html: green builds now with no call needed, amber needs a real decision first, red needs an account this environment can't provision.

buildable now— no product decision, no vendor account, just code needs a decision— a real policy/pricing/commission call needs an account— a vendor or merchant credential this sandbox has no way to obtain
PAY-01Coach booking payments never charge — a booking activates for free
buildable now

coaching.service.ts's createBooking() confirms a session and copies a real priceCents onto the Booking row, but never creates a Payment — no checkout step exists anywhere in either coach or user app for a session booking. This is the exact same simplification Subscribe/Program Purchase shipped with before Razorpay closed that gap for them, and the code's own doc comment already calls it out as "a natural, contained follow-up": add booking to PaymentPurpose, extend resolveAmountCents() to resolve a ProfessionalServiceOffering's price, and gate createBooking() behind verifiedPayment: true exactly like subscribe()/purchaseProgram() already are. See §05 Phase 3.

PAY-02Currency / list-price decision
launch-blocking decision

The ~80x undercharge risk above — see §02 in full. Listed here too so it isn't lost inside a flat scan of this inventory: this is the single highest-priority item on this page.

PAY-03No real Razorpay merchant credentials in this build environment
needs an account

RAZORPAY_KEY_ID/RAZORPAY_KEY_SECRET/RAZORPAY_WEBHOOK_SECRET are all unset here — every payment route correctly 503s with payment_gateway_not_configured rather than crashing, but nothing in this integration has ever been exercised against a real Razorpay sandbox in this sandbox. Even just test-mode keys (rzp_test_...) from a real Razorpay dashboard signup would let the full order → checkout → verify → webhook loop run for real for the first time.

PAY-07Razorpay's own fee/tax fields are received and discarded
buildable now

Razorpay's payment.captured webhook payload carries the gateway's own fee/tax figures on the payment entity (its cut of the transaction, in paisa) — handleWebhook() already destructures that exact object (event.payload.payment.entity) but only ever reads .id/.order_id off it today. Persisting the two fields is a small, real, decision-free improvement: it's the one piece Payment is missing to show a genuine Gross → Fee → Net breakdown, not the fabricated multi-row ledger PAY-08 below flags as still out of reach. See §05 Phase 1.

PAY-0906.03's "gateway health" indicator has nothing real behind it
buildable now

adminPayments.service.ts lists gatewayHealth in notAvailable today because no uptime/incident tracking exists for Razorpay — correctly not faked as "healthy." A real, honestly-labeled proxy needs zero new infrastructure: the most recent webhook-touched Payment.updatedAt already tells you how long it's been since Razorpay last reached this app. Ship it as "last gateway event received Xh ago," not an invented uptime percentage. See §05 Phase 2.

PAY-14Abandoned checkout orders never expire or get reconciled
buildable now

A user who opens checkout and never completes it leaves a Payment row stuck at status: "created" forever — no cron/cleanup job, no TTL, nothing marks it stale. Low-stakes today (an unpaid order grants nothing), but it'll clutter the Payments Directory and skew "success rate" once real volume shows up. A scheduled job flipping any created row older than, say, 24h to a new expired status is contained, low-risk cleanup — no product decision required, just an enum value and a job.

PAY-0806.02's ledger-flow card shows one line item, not a real breakdown
partially unlocked by PAY-07, rest needs PAY-05

Today it renders the one real number this build tracks — gross amountCents — rather than a fabricated discounts/fees/tax breakdown. PAY-07 lands the fee/tax half for real with no decision needed. The discount line still needs PAY-05's Coupon decision, and the tax line needs TaxConfig (already real, Module 10) actually linked per-transaction, which nothing does yet.

PAY-04No refund flow anywhere — mobile, backend, or admin
needs a refund policy

No Refund entity exists (sketched but never built — docs/admin/06-data-model.md §2: "linked to a transaction, with reason/approver/status"). cancelSubscription() just flips status to canceled with no refund; programPurchases has no cancel path at all; the Razorpay Node SDK already installed here exposes a real payments.refund() call that's never invoked anywhere in this codebase. Admin's 06.04 Refunds screen is deferred whole — "empty by construction," no submission path exists to populate it. Decision needed: a refund window/policy (full refund within N hours? prorated? case-by-case admin approval only?) — once picked, the entity, the real API call, and the screen are all straightforwardly buildable. See §05 Phase 4.

PAY-05No discount/coupon mechanism anywhere in checkout
needs a discount-program decision

No Coupon entity, no discount-code field on createOrderSchema, nothing in resolveAmountCents() that could apply one. Blocks 06.05 Pricing's Coupons half (the Plans half already shipped 25 Aug 2026) and is one of the three missing stages in PAY-06 below. Decision needed: whether a discount program exists at all for launch, and if so its shape (percentage-off, flat amount, first-month-only, referral-tied) — see also the Refer & Invite reward gap already flagged in docs/mobile/07-open-questions-gaps.md §20, which is the same missing-mechanism problem from the referral side.

PAY-0606.01 Commerce Revenue Dashboard ("waterfall") — deferred whole
compound blocker — 3 upstream gaps

Needs a real Gross → Discounts → Gateway fees → Refunds → Settlements → Net chain. Discounts needs PAY-05, Refunds needs PAY-04, Settlements needs PAY-10 below — three separate open decisions, not one. Rendering it with half the stages real and half invented would misrepresent actual revenue, worse than the usual honest gap — correctly deferred whole rather than built as a partial chart. Gateway fees (PAY-07) is the one stage of six that's genuinely unblocked today.

PAY-10Coach Settlements & Influencer Payouts (10.06/10.07)
needs a commission decision, then PAY-01

Already fully investigated and documented in reports/finance-architecture-plan.html §04 — not re-litigated here, only cross-referenced. Two stacked blockers: no commission/take-rate has been decided anywhere in this build, and even once one is, there's still no real coaching-payment data to settle against until PAY-01 (booking payments) is real. CoachSettlement/InfluencerPayout are deliberately not modeled yet — see that doc for the full reasoning and the "one ledger" architecture they'll join once unblocked.

PAY-11Bank/Payment Accounts live sync (10.09)
needs a banking vendor account

Also already covered in reports/finance-architecture-plan.html §04 — a "sync"/live-balance screen describes real bank connectivity (a Plaid-equivalent, or Razorpay's own settlement/virtual-account APIs), not a stored record. No schema proposed there or here; genuinely needs an account to acquire, not a decision to make.

PAY-12Subscription plan switches have no proration
low-priority policy decision

subscribe()'s own doc comment already calls this out: switching plans while one is active/trialing cancels the old one and starts the new one at full price, no partial-period credit. Explicitly framed as "a real simplification... but an honest one — nothing here claims to charge money it doesn't." Worth a real decision once billing volume matters, not urgent before then.

PAY-13Checkout is a WebView, not the native Razorpay SDK
low-priority UX decision

RazorpayCheckoutModal.tsx loads Razorpay's hosted checkout.js inside a react-native-webview — a real, working integration, deliberately chosen because the native SDK needs native module linking (a custom dev client/EAS build), which this app's plain Expo managed workflow doesn't have. Functionally complete; the only gap is UX polish the native SDK would add (saved cards, deeper UPI-app handoff). Not blocking real transactions, worth revisiting only if a native build is ever produced for other reasons.

Nothing above is buildable without real credentials to test against

Every "buildable now" item in §03 can be written and type-checked in this sandbox exactly like the rest of this build, but — per this environment's own standing limitation — none of it can be live-verified against an actual Razorpay account, because none exists here (PAY-03). Test-mode keys are enough; a live account isn't needed until PAY-02 is actually resolved.
