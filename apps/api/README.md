# api

Shared backend API — serves `user-mobile` (Phase 0/1/2/3/4) and, as of 20 Aug 2026, both `admin-web`'s first slice (Phase 6) and `coach-mobile`'s first slice (Phase 5) — see [../../docs/platform/roadmap.md](../../docs/platform/roadmap.md). Implements the entities in [`../../docs/admin/06-data-model.md`](../../docs/admin/06-data-model.md) and enforces auth on every route — see [`../../docs/admin/05-roles-permissions.md`](../../docs/admin/05-roles-permissions.md) for the RBAC matrix. **25 Aug 2026:** every admin role is now actually enforced, not just assignable — see the "Go-live hardening" section below; this paragraph's older "only `super_admin` is enforced" claim (gap §7) no longer holds.

**Stack:** Node.js + TypeScript + Express, Zod for request validation, Prisma + PostgreSQL, JWT access/refresh auth. See [`../../docs/platform/project-structure.md`](../../docs/platform/project-structure.md) §2 for the rationale.

**Phase 0/1/2/3/4 scope:** auth (signup/login/refresh/logout), user profile + onboarding + profile/preferences updates, read-only Programs/Exercises/Recipes plus a real Exercise Detail (seeded step-by-step `instructions` and a computed same-muscle-group `alternatives` list, no video — gap §26), the core Training flow — Program Detail, Workout Detail, and WorkoutSession logging (start/log-set/complete, plus, added 20 Aug 2026, a real abandon — gap §33's explicit-button half) — the core Nutrition flow — Recipe Detail, MealLog logging (from a recipe or manual macro entry), and WaterLog logging (a simple "+1 glass" quick-add) — Progress & Body — BodyMeasurement logging plus Personal Records computed from WorkoutSession data, and (added 19 Aug 2026) ProgressPhoto CRUD — real capture/upload storage with no object-storage backend, see gap §34 — Timeline — a real "milestone spine" (PRs, workout-count milestones, program completions) computed live from existing data, no stored `TimelineEvent` table — **AI Coach (added 25 Aug 2026, `modules/aiCoach`)** — real chat backed by conversation persistence, a system prompt grounded in the user's actual goals/recent workouts/latest measurement, a per-user rate limit, and a bounded replay history; 503s honestly when no AI provider is configured rather than faking a reply — closes gap §13's AI Coach half, leaving Recovery & Devices (needs real Bluetooth/HealthKit/Google Fit integration and hardware this build has no access to) as Phase 2's one still-unbuilt piece — monetization: Subscription & Payments (list plans, subscribe/switch/cancel, purchase history against `SubscriptionPlan`/`Subscription`, plus, added 19 Aug 2026, real seeded annual plan variants for Pro/Elite backing a Monthly/Annual toggle — see gap §35) and Programs Commerce (one-off Program purchases against a new `ProgramPurchase` model, plus a real entitlement gate on starting a priced program's workouts) — **20 Aug 2026: both now require a real, verified Razorpay payment for any non-free plan/program (`modules/payments`, gap §38), closing gap §14** — and Reminders (full CRUD against a new `Reminder` model, backing purely local on-device notifications on the client — no server-push here, see gap §16; this module also has the API's first real DELETE endpoint, since a reminder is a deletable setting rather than history) — plus Settings: a Notification Settings master toggle (`User.notificationsEnabled`), Security (real password change that revokes every active session, an active-sessions list/revoke against the existing `RefreshToken` model, a GDPR-style full data export, and account deletion — all reusing `User`/`RefreshToken`, no new tables), Support (full ticket create + list against a new `SupportTicket` model — the mobile-writable subset only; status/priority/assignee/reply-thread progression is a Phase 6 admin-console concern, see gap §19), and Referral (every user gets a real, unique `User.referralCode` generated at signup; signup accepts an optional referral code and, if it matches a real user, creates a genuine `Referral` attribution row; `GET /referrals/me` returns the code plus a real referred-signup count — no reward/bonus mechanism exists yet, see gap §20) — **Two-Factor Authentication (added 25 Aug 2026, `lib/twoFactor.ts`)** — real TOTP (RFC 6238, `otplib`), not SMS: `POST /users/me/2fa/setup` generates and encrypts (AES-256-GCM) a secret and returns a QR code (`qrcode` npm package) + manual-entry string; `POST /users/me/2fa/enable` requires a live 6-digit code before flipping `User.twoFactorEnabled` and returns 10 single-use bcrypt-hashed recovery codes in plaintext once; `POST /users/me/2fa/disable` requires the account password; `POST /auth/2fa/verify` completes login using a short-lived (5-minute) JWT "challenge token" issued by `/auth/login` in place of real session tokens whenever 2FA is on, so a second factor is enforced before any session token is ever handed out — closes gap §17, correcting its original "needs an SMS/TOTP provider decision" framing: SMS 2FA genuinely needs a third-party gateway account (same blocker as gap §9's phone+OTP), but TOTP needs none, only a server-generated key (`TWO_FACTOR_ENCRYPTION_KEY`, required/fail-fast like the JWT secrets) — seeded not admin-authored yet — see `scripts/seed.ts`. Not built yet: FoodItem (barcode catalog), MealPlan, RecoveryMetric, AIInsight, Coach/CoachBooking — add each in the phase that needs it (see [`../../docs/mobile/05-data-model.md`](../../docs/mobile/05-data-model.md) §2 for the full target model). `Payment` (added 20 Aug 2026, gap §38) now covers the real-money-transaction role that list used to name as unbuilt "Transactions".

## Go-live hardening (25 Aug 2026)

A pass of real production-readiness fixes ahead of a weekend launch of the consumer app (`user-mobile`, deployed as a web build) and the admin console — prompted by an honest audit that found this API had never actually booted against a live database, had zero rate limiting, zero error monitoring, and only `super_admin` genuinely enforced despite all 8 `AdminRole` values being assignable.

- **RBAC is now real.** `middleware/adminPermissions.ts` adds `requirePermission(module, action)`, applied to every admin route. `super_admin`'s matrix is copied directly from `docs/admin/05-roles-permissions.md`'s real design-sourced permission table (with one deliberate extension — `commerce` gains `create`/`edit` to match what `adminPlans` routes have actually always allowed, since that doc's matrix pre-dates Module 06.05). The other 7 roles get a **starter matrix**, not a confirmed spec: each role is granted exactly what `super_admin` has on the one matrix row matching that role's own stated scope from the same doc (e.g. Finance = "Revenue, transactions, settlements" → the same access as `super_admin`'s `commerce` row, nothing else). Review this against your actual staff roster before real non-`super_admin` accounts rely on it — see `adminPermissions.ts`'s own doc comment for the full per-role reasoning.
- **Rate limiting** (`middleware/rateLimit.ts`, `express-rate-limit`) on every login endpoint (`/auth/login`, `/admin/auth/login`, `/professionals/auth/login` — 10/15min) and every signup/payment-order endpoint (`/auth/signup`, `/professionals/auth/signup`, `/payments/razorpay/orders`, `/payments/razorpay/verify` — 30/15min). In-memory store — correct for this build's single-instance deployment, not for a future multi-instance one (see that file's own comment).
- **CORS fails fast in production** instead of silently defaulting either wide-open or blocking the real frontend — `config/env.ts` now refuses to boot with `NODE_ENV=production` and an empty `CORS_ORIGINS`.
- **A live Razorpay key can't boot without confirming the currency fix.** `PRICE_CURRENCY_CONFIRMED` must be `"true"` before a `rzp_live_...` key is accepted — see `config/env.ts` and `.env.example`. Test keys (`rzp_test_...`) are unaffected, so a real test-mode transaction can still be run before that decision is finalized.
- **Error monitoring** (`lib/sentry.ts`, `@sentry/node`) — optional via `SENTRY_DSN`, same "unconfigured means quietly off" pattern as Razorpay/AI. Wired into the global error handler plus `uncaughtException`/`unhandledRejection`.
- **Graceful shutdown** — `index.ts` now handles `SIGTERM`/`SIGINT` (most PaaS platforms send `SIGTERM` on redeploy) by closing the HTTP server and disconnecting Prisma cleanly instead of hard-killing in-flight requests.
- **`trust proxy` is now set** (`app.ts`) — caught while writing the deploy config, not something the earlier hardening pass had reason to think about: without it, every request behind Render's load balancer would report the same IP address, which silently breaks the rate limiting above (every user sharing one bucket) rather than crashing loudly. See that line's own comment.
- **An admin can finally rotate their own password — API and UI both.** `PATCH /admin/auth/password` (`adminAuth.routes.ts`) plus `apps/admin-web`'s new 12.05 Security screen (`SecurityScreen.tsx`, Admin & System's fourth sub-nav item) — found while writing the deploy runbook's seeding step: `scripts/seed.ts`'s bootstrap super_admin had no path off its initial credential except editing the database directly, and that initial credential (`SEED_ADMIN_PASSWORD`, defaulting to a value published in this repo's own `RUN-LOCALLY.md`) is exactly the kind of thing that needs to be rotatable. Mirrors `users.service.ts`'s consumer-facing `changePassword` on the backend; the screen was built and verified with a real Playwright run (not just typecheck) once the first pass shipped the endpoint with no UI calling it — see `SecurityScreen.tsx`'s own doc comment for why only password-change is real out of 12.05's fuller Figma spec. `render.yaml` and `DEPLOY-RUNBOOK.md` now also make `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` a required step, not an easy-to-skip optional one, so the published default never actually reaches a production database in the first place.
- **Razorpay signature checks are now constant-time.** `modules/payments/payments.service.ts`'s webhook and client-verify signature comparisons both used plain `!==`, which leaks timing information about how many leading bytes of a forged signature were correct — the exact side-channel `crypto.timingSafeEqual` exists to close, and why Razorpay's own SDK ships a constant-time helper rather than telling integrators to compare with `===`. Found while doing a final sweep for this class of gap alongside the other hardening above; both call sites now go through a shared `timingSafeEqualHex()` that also guards the length check `timingSafeEqual` itself doesn't (it throws on mismatched-length buffers rather than returning false).
- **Not fixed here, still real gaps:** the actual boot-against-a-live-database test (this sandbox still can't reach `binaries.prisma.sh` — see "Note on this scaffold" below) and the Razorpay currency/pricing decision itself (a business call, not a code fix — see `PRICE_CURRENCY_CONFIRMED` above).

> **Note on this scaffold:** `prisma generate` could not run inside the cloud sandbox this was built in — its query-engine binary download (`binaries.prisma.sh`) isn't reachable from that environment's network allowlist. Confirmed this also blocks `prisma validate`, so the Training-flow (`Workout`, `WorkoutExercise`, `WorkoutSession`, `ExerciseSetLog`), Nutrition-flow (`MealLog`, `WaterLog`, plus the `proteinG`/`carbsG`/`fatG` fields added to `Recipe`), Progress-flow (`BodyMeasurement`, then `ProgressPhoto`), and Commerce-flow (`SubscriptionPlan`/`Subscription`, then `ProgramPurchase`) schema additions were manually reviewed for relational/enum consistency rather than tool-validated. This is an infrastructure limitation of that sandbox, not a code issue — `npm run db:generate` (and `db:migrate`) will work normally on a developer machine or in CI, and that's the real validation this schema still needs. Everything else (Express app, Zod schemas, JWT/password logic, route wiring) was typechecked and linted clean; the one remaining TypeScript error until you run `db:generate` locally is `users.service.ts` failing to import the `User` type from `@prisma/client`, which resolves the moment the client is generated. (`apps/api/src/modules/progress/progress.service.ts`, `apps/api/src/modules/programPurchases/programPurchases.service.ts`, and (added 19 Aug 2026, for Workout History's `listHistory`) `apps/api/src/modules/workoutSessions/workoutSessions.service.ts` explicitly type callback params / avoid `.map()`/`.filter()` on raw query results for the same reason — see the code comments there — so that error doesn't multiply.) **20 Aug 2026, confirmed by actually attempting to boot it:** this isn't just a typecheck-time gap — the server can't start at all in this sandbox. `db/prisma.ts` instantiates `new PrismaClient()` eagerly at module load (imported transitively by nearly every route), and the un-generated `@prisma/client` package throws synchronously the moment that runs: `Error: @prisma/client did not initialize yet. Please run "prisma generate" and try to import it again.` — confirmed via `npx tsx src/index.ts` with dummy env vars, crashing before the process ever calls `app.listen()`. On a machine that can reach `binaries.prisma.sh`, `npm run db:generate` replaces the placeholder with a real generated client and this resolves itself; there's nothing else to fix here.
