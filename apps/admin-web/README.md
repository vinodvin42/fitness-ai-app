## Stack

React 18 + TypeScript + Vite + Tailwind CSS v4 + TanStack React Query + React Router + Recharts, per `docs/platform/project-structure.md` §2's recommendation. A CSR SPA, not Next.js — this console is entirely authenticated, data-table/dashboard-heavy, with no public/SEO surface, so client-side rendering is sufficient.

### Why React 18, not 19

`apps/user-mobile` pins React `18.2.0` (an Expo SDK 51 requirement). This is an npm workspaces monorepo, so a second major React version installed anywhere in the tree risks two copies of React coexisting at runtime — components rendered by one copy calling hooks that resolve against the other, which throws (`Cannot read properties of null (reading 'useRef')`) at the first hook call. This was hit and fixed during this app's own scaffolding: root `package.json` now carries an `overrides` block pinning `react`/`react-dom` to `18.2.0` workspace-wide, and `admin-web`'s own `package.json` matches that pin exactly. If a future phase drops the mobile app's React 18 constraint, revisit this — Recharts, React Query, and React Router here all already support React 19.

## Decisions made resolving the Figma-review gaps (`docs/admin/07-open-questions-gaps.md`)

This slice resolves several of that doc's open gaps as pragmatic, documented defaults rather than blocking on a design pass — the same discipline `apps/user-mobile` applied to its own equivalent gaps:

- **Gap §1 (no auth screens designed):** built a plain, functional, undesigned login screen. No signup/MFA/SSO/password-reset — see `apps/api/src/modules/adminAuth/adminAuth.schema.ts`'s doc comment. **Bug fix, 25 Aug 2026:** `/login` rendered `LoginScreen` unconditionally with no redirect on success — `AuthProvider`'s `adminUser` state updated after `login()`, but nothing navigated away, so a correct sign-in just left the form sitting there. Found while building a mock-data demo of this app (see below) and confirmed against the real code, not simulation-specific. Fixed with `RedirectIfAuthed` in `App.tsx`, the inverse of the existing `RequireAuth` — same isLoading/adminUser check, opposite direction (redirects to `/` once authed, instead of to `/login` once not).
- **Gap §2 (inconsistent sidebar patterns):** standardized on the doc's own recommendation — primary icon+label rail, with a contextual sub-panel to be added once any module ships more than one screen. **21 Aug 2026:** Module 03 is the first to trigger this — `AppShell` now takes an optional `subNav` prop (pill row under the header); Professionals uses it for Directory/Credential Verification. Relationships and Users (same day) don't use it yet — each only ships one top-level screen (Directory; Detail/Profile is a row-click drill-down). **22 Aug 2026:** Admin & System (`/admin-system`) is a special case — it represents all 8 of Module 12's sub-screens in the Figma, but only 12.01 is built so far, so rather than a premature one-pill `subNav`, `/admin-system` routes directly to `AdminUsersScreen`. Revisit once 12.02+ ships. **Same day, Module 12.03 — Audit Logs:** the revisit arrived the same day — 12.03 is Module 12's second real screen, so `screens/adminAccounts/` was renamed to `screens/adminSystem/` (matching the "one screens folder per Figma module" convention every other module already follows) and a new `ADMIN_SYSTEM_SUB_NAV` (`screens/adminSystem/subNav.ts`) now covers both `/admin-system` and `/admin-system/audit-logs`, same pattern as Professionals/Programs. The backend module folder `apps/api/src/modules/adminAccounts` was deliberately left unrenamed — it's specifically the 12.01 admin-account-management service, a narrower concern than "all of Module 12," and `adminAuditLogs` is its own separate backend module. **Same day, Module 05 — Programs:** the second module (after Professionals) to use `subNav` from day one — `PROGRAMS_SUB_NAV` covers all established for Overview/Clients/Sessions/etc. **Same day, Module 06.05 — Pricing:** the trigger finally arrives for Commerce too — Pricing is its second nav-level screen, so nav-level screen, so `screens/relationships/subNav.ts`'s `RELATIONSHIPS_SUB_NAV` now covers `/relationships` (Directory) and `/relationships/change-queue` (the Queue); Detail remains a row-click drill-down, not a nav destination. Gaps §3, §5, §7, §8, §11 remain open — they need a product/design answer this build can't make (see the gaps doc itself). Gap §4 (Commerce/Finance ledger question) was resolved 26 Aug 2026 — see above.

## Local development

```bash
npm install                                  # from the repo root (npm workspaces)
cp apps/admin-web/.env.example apps/admin-web/.env.local
npm run dev:admin                            # starts Vite on http://localhost:5173

# apps/api must also be running (see apps/api/README.md) with a seeded
# admin account:
npm run db:seed --workspace=apps/api         # seeds admin@fynrox.com / ChangeMe123!
                                              # (override with SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD)
```

`npm run typecheck` / `npm run lint` / `npm run build` all run clean in this build sandbox. `build` could not be *smoke-tested against a live API* here — same sandbox limitation as the rest of this repo (`prisma generate` can't reach `binaries.prisma.sh`, so `apps/api` can't boot in this environment at all, see `docs/platform/mvp-launch-plan.md` §2). The Dashboard screen's rendering itself was verified with mocked API responses (Playwright, screenshotted) rather than a live backend.
