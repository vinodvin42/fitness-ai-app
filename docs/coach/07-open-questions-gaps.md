# Open Questions & Gaps — Coach App

Read alongside [../09-open-questions-gaps.md](../admin/07-open-questions-gaps.md) (admin) and [../mobile/07-open-questions-gaps.md](../mobile/07-open-questions-gaps.md) (consumer app) — the recurring gaps (no auth flows fully specified where relevant, no empty/loading/error states, no published design tokens, iOS-only) apply here too and aren't repeated below.

## 1. Coach discovery/booking is designed twice, inconsistently — highest-priority item across all three files
Full comparison in [06-cross-app-integration.md](06-cross-app-integration.md) §2. This is the single most consequential inconsistency found across the whole project so far: two different screen flows, two different coach-category taxonomies (one of which — Yoga/Sports in the consumer app — doesn't exist anywhere else in the product), and two different booking flow shapes. **This needs a product/design decision before any backend or frontend work on coaching discovery/booking starts**, or engineering will end up building against whichever version it happens to see first, and rework will follow.

## 2. Bottom-nav labels have now drifted three ways
- Consumer app (`v1-user`): Today, Train, Fuel, Recover, More.
- Coach app (`v1-coach`, coach-side): Dashboard, Clients, Calendar, Messages, More.
- Coach app (`v1-coach`, `user-my-professional-team` screen): Home, Explore, Sessions, Messages, Profile.
The first two are arguably fine — they're two different apps for two different roles and can reasonably have different tab sets. The third is the problem: it's a *user-facing* screen (part of the consumer journey) that doesn't match the consumer app's own established tab bar. **Recommend:** fix `user-my-professional-team` (and any other `user-`-prefixed screens in this file) to use the consumer app's actual tab bar before implementation, and treat this as a signal to double-check the rest of this file's `user-` screens for the same drift.

## 3. Three different default accent colors across three apps
Admin = mint green, consumer app = blue, coach app = lime/yellow-green (see [04-design-system.md](04-design-system.md) §1). Given the consumer app also supports a *user-selectable* accent color, one plausible resolution: pick one brand-default accent (mint green, since it's used in the admin console and is closest to "PrimeFit green" implied by the leaf/nutrition iconography across all three files) and treat blue and lime as either legacy/inconsistent choices to fix, or intentional per-role defaults to keep. Needs a design decision, not an engineering guess — this blocks defining the shared `packages/ui` token set in [../07-project-structure.md](../platform/project-structure.md).

## 4. Calendar, Messages, and More tabs have zero screens
Only Dashboard and one Clients destination were actually designed for the coach app's own shell. Messages is a particularly notable gap given the consumer app has a fully designed `user-coach-messaging` screen (with shared plan/video cards) — the coach's side of that same conversation doesn't exist yet anywhere. **Action needed:** these need a design pass before they can be scoped for the roadmap.

**25 Aug 2026 — re-checked, still genuinely open.** Re-reviewed while working through the coach app's remaining gaps after Discovery & Booking shipped (gap §1). Unlike gap §1, this one has no unblocked half to build ahead of the decision: Calendar has no spec for what a coach's calendar should even show (an editable availability grid? a read-only upcoming-sessions list? something else — a real `Booking` entity exists as of 25 Aug 2026, so data isn't the blocker, a UI/UX decision is); Messages needs both a design AND a `Message` data model/delivery mechanism that doesn't exist anywhere in this build yet, on either app; More has zero frames to build against at all, on either app or role, unlike apps/user-mobile's own More tab (§N), which was designed. `apps/coach-mobile/src/navigation/MainTabs.tsx` continues to render all three as real, honest "Coming soon" screens rather than inventing layouts with no design source — the same discipline this build has held to for every other undesigned screen (Body Composition, Recovery & Devices, live chat support, and others).

## 5. No coach-side earnings/payout visibility
The admin console tracks Coach Settlements (10.06) with a Hold/Approve workflow, but no screen in this file lets a coach see their own upcoming or past payouts, session earnings breakdown, or settlement status. This is a reasonable early ask from real coaches (self-service earnings visibility) and is currently a complete gap between what admin manages and what a coach can see about their own money.

## 6. "Create Workout Plan" / "Create Nutrition Plan" have no destination
Both dashboard variants surface these as primary quick actions, but no content-authoring screen exists in this file (and the consumer-app content — Programs/Exercises/Recipes — is admin-authored per [../mobile/06-cross-app-integration.md](../mobile/06-cross-app-integration.md) §1, not obviously coach-authored). **Decision needed:** can individual coaches author their own workout/nutrition plans for their clients (distinct from the admin-managed content library), or do these buttons route into assigning existing admin-approved programs? This changes both the coach app's scope and the Programs data model in [../06-data-model.md](../admin/06-data-model.md).

## 7. KYC (Aadhaar) collection needs explicit privacy handling
The credential-verification screen collects a government ID (Aadhaar, India's national ID) directly in an onboarding upload flow. This is highly sensitive PII and should be handled with explicit, scoped consent and secure storage/redaction practices — worth an explicit security/privacy review before this screen is implemented, separate from the general privacy gaps already noted for the consumer app's onboarding ([../mobile/07-open-questions-gaps.md](../mobile/07-open-questions-gaps.md) §5).

## 20 Sep 2026 — R2 Wave 1: Professional's real account-level lifecycle (application -> verification -> approved -> available) ships, schema + service layer only

Developer 2's real R1 work package §2 names the full Professional lifecycle as `APPLICATION -> VERIFICATION -> APPROVED -> AVAILABLE -> OFFERED/ASSIGNED -> ACCEPTED -> AWAITING_PAYMENT -> RELATIONSHIP_ACTIVATING -> ACTIVE -> DELIVERY -> COMPLETED/CHANGED/ENDED`. Before this wave, none of it existed as real state — `Professional.status` was only ever `active`/`suspended`, and service-specific approval already existed for real via `ProfessionalCredential.status` (untouched by this wave, still the genuine per-(professional, serviceType) approval mechanism). This wave built only the first four stages — the professional's own account, before any specific client relationship exists. Everything from OFFERED onward is about a specific `Relationship` row (already real, `coaching.service.ts`'s own scope) and remains later waves' work — this wave does not touch `coaching.service.ts`'s `Relationship` logic at all.

**What shipped:**
- **Schema:** `Professional.lifecycleStatus` (new `ProfessionalLifecycleStatus` enum: `application | verification | approved | available | suspended`) and `Professional.maxActiveClients` (`Int`, default 15) — both purely additive, alongside `Professional.status` and `ProfessionalCredential.status`, neither of which was renamed or redesigned. See `apps/api/prisma/schema.prisma`'s own doc comment on the enum for the exact, documented interaction between all three fields: `Professional.status === "suspended"` is always the authoritative "can this professional do anything" gate regardless of what `lifecycleStatus` reads.
- **Backfill** (`prisma/migrations/20260920083029_professional_lifecycle`): every existing `Professional` row (not only `status: active` ones — see the migration file's own comment for why `suspended` rows get the identical treatment) backfilled from real signals — `>= 1 verified ProfessionalCredential` → `available`, zero verified credentials → `approved`. Verified locally against the seeded coaches (`coach-alex-rivera`/`coach-priya-nair`/`coach-jordan-blake`, all `status: active` with a verified credential) — all three landed on `available`, `maxActiveClients: 15`, confirmed by a direct `psql` query, not just trusting the migration ran.
- **Service layer** (`apps/api/src/modules/professionalLifecycle/professionalLifecycle.service.ts`, new module — see its own top comment for why it isn't inside `professionalOnboarding` or `adminProfessionals`): `transitionToVerification` (system-driven, wired into `professionalOnboarding.service.ts#submitCredential`'s real first-submission moment), `maybeAdvanceToApproved` (admin-driven, wired into `adminProfessionals.service.ts`'s `verifyCredential`/`verifyKyc`, requires BOTH KYC and >= 1 credential verified), `recomputeAvailability` (system-driven, the single authoritative `approved <-> available` boundary — moves in both directions, so rejecting a professional's only verified credential demotes them back out of `available`, not just a one-way promotion), and `suspendLifecycle`/`restoreLifecycleAfterReactivation` (wired into the existing `suspendProfessional`/`reactivateProfessional`, which previously left `lifecycleStatus` stale through a suspend/reactivate cycle). Every transition writes a real `recordAudit()` entry.
- **Availability toggle:** `PUT /professionals/me/capacity` (professional-facing) and `PATCH /admin/professionals/:id/capacity` (admin-facing) both call the same `updateMaxActiveClients`; `GET /professionals/me/lifecycle` returns the real computed summary. `isAvailableForNewClients(professionalId)` is exported for later callers (`activeRelationshipCount < maxActiveClients AND lifecycleStatus === "available" AND status !== "suspended"`).

**One real design decision made this wave, not left implicit:** the work package left `approved -> available` as "automatic, or admin opt-in — your call, but make it consistent." Decided: fully automatic, driven by the same `recomputeAvailability` function that also handles the reverse demotion — a professional never needs a separate "go live" action once they hold a verified credential, and there's exactly one function that owns that boundary in both directions rather than two disconnected code paths that could disagree. A future wave that wants an explicit "open for new clients" opt-in (independent of the credential precondition) would need a real product decision to add a *second* gate on top of this one, not to change this one.

**No dedicated field was added to snapshot pre-suspension lifecycle stage.** Suspend/reactivate restoration reads the most recent `professional.lifecycle.suspended` `AuditLog` entry's `metadata.previousLifecycleStatus` instead of a new schema column — reuses the existing "every transition writes a real audit entry" infrastructure rather than adding a column whose only job is a single restore path. Falls back to a real recompute from current signals (not a fabricated guess) for the one case this can't cover: an account suspended before this wave shipped, with no such audit entry to read.

## 20 Sep 2026 — R2 Wave 2: Client 360 ships, gated on real `health_data_processing` Consent (not just an active Relationship)

Closes the gap an earlier audit flagged as most safety-critical: `getClientProfile`/`ClientProfileScreen.tsx` (6 Sep 2026 entry above) surface real `Booking`/`OnboardingProfile` data gated on nothing but an active `Relationship` — no assessment/training/nutrition/check-in summary was surfaced anywhere, and nothing anywhere checked the real `Consent` model (`prisma/schema.prisma`'s `Consent`/`ConsentType`, `users.service.ts`'s `listConsents`/`updateConsent`, both real since 18 Sep 2026) before a coach could see a client's actual health data. A coach with an active Relationship could, in principle, have been handed real health data the client never consented to share with a coach specifically — Consent's own `granted` flag was never read by anything on the coach side.

**What shipped, and the exact gating mechanism.** A new `GET /professionals/me/clients/:userId/summary` (`professionalClients.service.ts`'s `getClientSummary`) applies TWO checks, in order: (1) the same active-`Relationship` 404-not-403 gate `getClientProfile` already established (reused, not reinvented); (2) a real query of that user's own `Consent` row for `type: "health_data_processing"` — only `granted: true` unlocks health data. No consent (or a row that reads `granted: false`, including "never set" — same honest default `listConsents` already uses) returns `{ consentGranted: false }` and nothing else; `apps/coach-mobile`'s `ClientSummarySection` renders a real, honest "this client hasn't enabled data sharing yet" card for that state, not a blank or broken-looking one. This is the same "a real, checked precondition, never an implicit one" discipline `SafetyEscalation` already established for sensitive data in this codebase — Consent's `granted` boolean is now actually load-bearing on the coach side, not just a user-facing settings toggle nothing else reads.

When consent IS granted, the response aggregates real, recent (last 30 days, capped at 10 rows each) `WorkoutSession` completion/status (not per-set `ExerciseSetLog` detail — a coach needs adherence, not a full log replay), `MealLog` entries, `CheckIn` rows, and `BodyMeasurement` rows.

**Decision made, not guessed permissive: `ProgressPhoto` and `AiCoachMessage` content stay OFF even with consent granted.** No local evidence — this file, `prisma/schema.prisma`, or Developer 2's R1 work package as it exists in this repo — establishes either as coach-visible. The same work package's own Gym Partner Lite section (§5, `gyms.service.ts`'s `getMemberActivationSummary()`) explicitly treats photo/AI-conversation data as always off-limits to a non-owner party, which is the closest real precedent this build has, and it points OFF. Given this endpoint touches real user health/privacy data, the conservative default was preferred over guessing permissive — both are named explicitly in the response's own `notAvailable: ["progressPhotos", "aiCoachConversation"]` rather than silently omitted, same "name what's withheld, don't just drop it" convention `CLIENT_SENSITIVE_NOT_AVAILABLE` already uses one file over. If a future wave finds explicit work-package evidence either should be coach-visible, this is a one-line change (add the real aggregate, drop the name from `notAvailable`) — not a redesign.

**Verified for real, not just 200-status checks.** `apps/api/tests/professionalClients.test.ts` (5 tests): no-Relationship 404, Relationship-but-no-consent → `{ consentGranted: false }`, consent-granted → real aggregated data asserted field-by-field against fixture rows actually created in the test (`expect.objectContaining` on each of training/nutrition/checkIns/bodyMeasurements, plus a direct Prisma read to cross-check), a revoke-consent-again case, and a 401 with no auth. Full local HTTP run against the real seeded coach (`alex.rivera@coach.23primefit.demo`) and a fresh signed-up client: confirmed the summary honestly withheld data with an active Relationship and no consent, then — after granting consent and creating one real `MealLog`/`CheckIn`/`BodyMeasurement` row via the real user-facing endpoints — confirmed the summary's JSON matched those rows field-by-field against a direct `docker exec ... psql` query, then confirmed revoking consent went back to `{ consentGranted: false }`. All fixture rows (consent, relationship, meal log, check-in, body measurement, the user itself) were deleted afterward and confirmed gone via a direct `SELECT count(*)`, not just assumed from the delete calls succeeding. `npm run typecheck` (all 4 workspaces) and `npm run lint --workspace=apps/coach-mobile` both clean; the full `apps/api` suite (29 files, 167 tests, including this new one) passes.

**What's left for later waves:** no `WorkoutSession` fixture-backed exercise-level detail (deliberately out of scope — see above); `apps/coach-mobile`'s Client 360 section is a flat set of cards appended below the existing profile, not the tabbed Overview/Training/Recovery/Progress/Notes layout `docs/coach/03-screen-inventory.md` names for this screen (same defensible-substitution precedent the 6 Sep 2026 entry above already flagged — no design source exists for that tabbed layout, and this wave didn't invent one); private coach-only notes (`CoachNote`) and the offer/assignment flow remain explicitly out of scope, per the work package's own wave boundaries.

**What's left for later waves:** any coach-mobile or admin-web UI (no screen reads `lifecycleStatus`/`maxActiveClients`/the new endpoints yet); the OFFERED/ASSIGNED relationship-level flow (a distinct, later Wave 2 unit per the work package, and the first real caller of `isAvailableForNewClients`); gym-affiliation-based auto-approval, once the parallel Wave 1 Gym unit lands (this wave deliberately doesn't reference Gym at all, per BR-PRO-003 — nothing here creates an implicit approval path off a future gym relation, since `available` is gated purely on the pre-existing, real `ProfessionalCredential.status`).

## 20 Sep 2026 — R2 Wave 2: `ProfessionalOffer` ships — the real OFFERED/ASSIGNED stage, plus coach-mobile UI

The gap flagged at the bottom of the 20 Sep 2026 R2 Wave 1 entry above — "the OFFERED/ASSIGNED relationship-level flow... and the first real caller of `isAvailableForNewClients`" — is now built. Developer 2's real R1 work package §2 names the professional lifecycle as `APPROVED -> AVAILABLE -> OFFERED/ASSIGNED -> ACCEPTED -> AWAITING_PAYMENT -> ...`, and this wave's audit confirmed a real `Relationship` state machine exists (`requested -> accepted -> awaiting_payment -> activating -> active -> ended`) but is exclusively USER-initiated — a consumer requests a specific coach. Nothing anywhere let an admin (or a future system) propose a specific `available` professional to a specific user.

**Real product decision made for this wave, not re-decided here: manual admin-proposes-a-specific-pro only, no auto-matching algorithm.** A new, parallel `ProfessionalOffer` model (`professionalId`, `userId`, `serviceType`, `status` — `offered|accepted|declined|expired` — `proposedByAdminId` nullable, `expiresAt` nullable but real/enforced once set, `createdAt`/`respondedAt`) — deliberately NOT an extension of `Relationship`/`RelationshipStatus`, which stays untouched (its own enum, its own state machine, same tested behavior as before this wave). `proposedByAdminId` is nullable specifically because the work package's own "OFFERED/ASSIGNED" naming treats a system-computed match as an equally valid proposer for a later wave — no auto-propose trigger was built this wave, the schema just leaves the door open.

**The convergence point:** `acceptOffer()` (`apps/api/src/modules/professionalOffers/professionalOffers.service.ts`) does not duplicate relationship-creation logic — it calls straight into `coaching.service.ts`'s own `claimRelationship()`, the exact function a user-initiated request creates a `Relationship` row through today, so both flows land on the same real downstream mechanism (payment -> activation -> active) without forking it. One genuine implementation call made explicitly, not silently: since the professional has already said yes by accepting the OFFER, `acceptOffer()` also calls the existing, separately real `acceptRelationship()` right after (only when the claimed relationship is a brand-new `requested` row — never when it reused an existing relationship in some other status), so the same coach isn't asked to approve the same user/service pairing twice through two differently-named screens. This composes two existing, unmodified functions; neither's own state machine was altered.

**What shipped:**
- `professionalOffers.service.ts`: `createOffer` (admin-driven, enforces the real `isAvailableForNewClients()` precondition — the first real caller of that function, closing the gap Wave 1 flagged), `acceptOffer`/`declineOffer` (coach-driven, atomic claim-once via `updateMany` + a `status: "offered"` filter, same discipline as `payments.service.ts#activatePayment`), `listOffersForProfessional`, `listOffers` (admin, filterable), `listAvailableProfessionals` (the thin "available professionals" read admin-web's picker needs).
- `apps/coach-mobile/src/screens/clients/PendingRequestsScreen.tsx` gained a real second section, "Offers from PrimeFit", below the existing Client Requests section — a deliberate choice not to merge the two into one indistinguishable list: a Relationship request already exists as its own row the moment a user asks for a coach; an offer is a separate row that only creates a Relationship once accepted. Real Accept/Decline actions wired to `GET /professionals/me/offers` and `POST /professionals/me/offers/:id/accept|decline`.
- 12 real Postgres-backed tests (`apps/api/tests/professionalOffers.test.ts`), including the `available`-precondition rejection and a genuine `Promise.all` concurrency test proving exactly one of two concurrent `acceptOffer()` calls wins and exactly one `Relationship` row results.
