# Translating the user app

The Definition of Done requires copy to be "in English and wired for
translation (no strings in code)". This is how that works here.

## What exists

- `src/i18n/index.ts` — initialises i18next and exposes
  `applyLanguagePreference()`.
- `src/i18n/locales/en.ts` — the English source catalogue, and the only
  place user-facing copy should live.
- The app already persisted a `languagePreference` across ten Indian
  languages before this; what was missing was anything that read it, so
  choosing a language changed nothing on screen.

## Why a library

Hindi, Tamil, Telugu, Bengali and the rest do not pluralise the way
English does. `count === 1 ? "professional" : "professionals"` is
correct in English and wrong in most of the languages this app offers,
and wrong *silently* — nothing fails, the sentence is just malformed for
the reader. i18next resolves plurals through CLDR rules per language,
which is the part that is genuinely hard and easy to get wrong.

## Using it in a screen

```tsx
import { useTranslation } from "react-i18next";

export function SomeScreen() {
  const { t } = useTranslation();
  return <Text>{t("some.key")}</Text>;
}
```

Interpolation: `t("checkout.pay", { amount: "₹999.00" })` against
`pay: "Pay {{amount}}"`.

Plurals: define `thing_one` and `thing_other` in the catalogue and call
`t("thing", { count })`. Never branch on the count in the component.

Keys are `screen.element`, matching the screen's file name, so the string
for a piece of UI is findable from the component and vice versa.

## Language selection

`AuthContext` applies the signed-in user's `languagePreference` in one
place — it wraps `setUser`, so every path that sets a user keeps the
language in step and a future call site cannot forget. Signing out
resets to English rather than leaving the previous user's language on
the sign-in screen.

## Which surfaces are covered

| Surface | State |
|---|---|
| `apps/user-mobile` | Complete — 518 strings to 0 |
| `apps/coach-mobile` | Complete — 159 to 0 (`i18n-coach.md`) |
| `apps/gym-portal` | Complete — 50 to 0 |
| `apps/creator-portal` | Complete — 46 to 0 |
| `apps/admin-web` | Complete — ~1,150 keys, migrated by script |
| `apps/landing` | **No mechanism at all** — see below |

**admin-web was migrated by script**, and that is worth explaining,
because nothing else here was. It is 65 components and over a thousand
strings, almost all of them table headers, option labels and stat
captions. Hand-authoring keys for those would have produced keys no more
informative than a slug of the English and taken longer to review than to
write. So `scripts/` grew three passes: props and single-line text nodes,
then multi-line text nodes, then text containing parentheses. Each pass
generates a key from the namespace (the file name minus "Screen") and a
camel-cased slug of the English, capped at four words and extended on
collision.

Six strings were migrated by hand afterwards, all for the same reason:
they wrapped a styled `<span>` or an interpolated value mid-sentence, and
a sentence with something pinned in the middle does not survive
translation.

**Two things render to a user and are deliberately NOT translatable**, and
`scripts/i18n-report.mjs` lists them explicitly rather than pattern-
matching: a URL placeholder (`https://…` means the same in every
language) and standard finance acronyms (CAC, LTV, ARPU, MRR — used
untranslated in Indian finance writing; an expansion would be less
recognisable, not more).

The scripted pass is verified, not assumed: a check reads every
`t("ns.key")` call site back out of the migrated files and asserts its
catalogue value appears verbatim in the pre-migration file from git. All
1,253 sites passed. Compiling proves nothing about whether a page still
says the same thing.

**`apps/landing` needs a different mechanism.** It is static HTML with no
build step and no framework — deliberately, per its own README. Porting
react-i18next there is not possible; the options are build-time
templating (which breaks the no-build-step property) or a runtime swap
driven by `data-i18n` attributes. Neither is a small decision, and the
second only translates for visitors with JavaScript, leaving search
engines and no-JS readers on English. That is a product call about
whether per-language URLs are wanted, not a mechanical retrofit.

**None of the four completed apps has a language preference to read**
except the user app. `User` has a `languagePreference` column;
`Professional`, `Gym` and `Influencer` do not. Each portal ships
`applyLanguagePreference()` ready and unused, and shows no language
selector — a picker that saved nowhere would be worse than none.

## What stops it drifting

Two things, because the failure mode here is silent.

**`apps/api/tests/i18nCatalogue.test.ts`** runs in CI and asserts:

1. every `t("...")` in this app resolves to a real key, and
2. every key in the catalogue is reached by some call site.

The first matters because **i18next renders the key itself when it cannot
find one**. A typo in `t("auth.login.titel")` does not throw, does not
fail typecheck, and did not fail any test before this file existed — it
puts the literal text `auth.login.titel` on a user's screen.

The second matters because a dead key is paid for nine times over. It
already found one: `common.loading` had been written for a loading state
that is an `ActivityIndicator` everywhere and renders no word at all.

That check understands runtime-built keys — ``t(`guidance.status.${s}.label`)``
becomes a pattern rather than being ignored. Its first draft did not, and
duly reported ten live keys as dead; a dead-code report that confidently
points at live code is worse than no report.

`src/i18n/index.ts` also warns on a missing key in development. Note the
`saveMissing: __DEV__` next to it — i18next only calls
`missingKeyHandler` when `saveMissing` is on, so without that line the
handler never runs.

**`scripts/i18n-report.mjs`** counts what is left, per component. The
retrofit is partial and will be for a while, so the useful measure is a
number that moves, not a binary that stays false:

```bash
node scripts/i18n-report.mjs            # summary
node scripts/i18n-report.mjs --strings  # + the strings still inline
```

It is a heuristic — it counts JSX text nodes and the string literals
passed to text-rendering props, does not understand strings assembled
from variables, and will occasionally flag something that is not user
facing. A direction of travel, not a score.

## Migration state

**Complete.** As of 29 Sep 2026, `scripts/i18n-report.mjs` reports:

- **115 components**, 89 of which call `t()`.
- **115 have no inline user-facing strings left.**
- **0 inline strings remain** (518 when the report was first written).

The signed-out flow went first, because it is the only part of the app a
user sees *before* their `languagePreference` has loaded, and it is where
someone who cannot read English gives up. Everything else followed.

Two things are deliberately NOT in the catalogue:

- **Product names** — `FynroX`, `FynroX AI`, and the plan tiers
  (Basic / Pro / Elite). Translating a tier would make a user's plan
  unrecognisable against their own receipt. `FynroX AI` now comes from
  `BRAND_AI_NAME` and the support address from `BRAND_SUPPORT_EMAIL`, in
  `packages/config` — the spec's "one constant so a rename is one change".
- **Server-supplied strings** — anything the API sends (a coupon error, a
  professional's name, a programme title). Those are the API's to
  translate, not the client's.

## Patterns worth copying

Three came up repeatedly, and all three fail silently rather than
crashing.

**A module-level label map has to become a key map.** `MEAL_LABELS`,
`REFUND_COPY`, `ROWS`, `COMPARISON_FEATURES`, `HOW_IT_WORKS`, `CATEGORIES`
and `stepLabel`/`statusPresentation`/`idleTimeoutLabel` all held copy
evaluated once at import. A translated string baked in there is whatever
language was active when the module first loaded, and never changes
again — switching language would quietly leave those labels behind. Each
now carries a key and resolves at render. Where the map also held a tone,
colour or icon, that stayed: a colour is a design decision, a sentence is
copy.

**A sentence with something styled in the middle does not survive
translation.** Profile rendered `Your code <bold>FX-ABC123</bold> has 3
signups so far` as one interpolated sentence; word order moves between
languages, so the code lands wherever the English put it. It is now a
label, the code, and a count.

**Hand-written plurals are wrong in most of the ten languages offered.**
`signup{n === 1 ? "" : "s"}` and `reward{n === 1 ? "" : "s"}` were both
correct in English and silently malformed elsewhere. Both are CLDR
plurals now, which is the entire reason i18next is here rather than a
lookup object.

## Testing

`tests/i18n.test.ts` is valid vitest and **does not currently run**.
Installing a test runner into this workspace fails with an npm arborist
bug:

```
npm error Cannot read properties of null (reading 'edgesOut')
```

raised while resolving vitest 4's optional peers. It reproduces whether
vitest is declared in this workspace, pinned to an exact version, or
hoisted to the workspace root. `apps/api`'s copy lives under
`apps/api/node_modules` and is not hoisted, so it cannot be borrowed.

Every assertion in that file was verified by running the same checks
through `tsx` directly — plain keys, interpolation, both plural forms,
the fallback for an untranslated language, an unsupported language code,
and a scan for empty strings. All passed. But the file is not covered by
CI today, and a green build should not be read as covering it.

Fixing this is worth doing: it is the only workspace with no way to
assert anything, and the i18n layer is precisely the kind of code that
fails silently.
