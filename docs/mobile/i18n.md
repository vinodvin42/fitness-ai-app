# Translating the user app

The Definition of Done requires copy to be "in English and wired for
translation (no strings in code)". This is how that works here.

## What exists

- `src/i18n/index.ts` — initialises i18next and exposes
  `applyLanguagePreference()`.
- `src/i18n/locales/en.ts` — the English source catalogue, and the only
  place user-facing copy should live.
- The app already persisted a `languagePreference` across ten Indian
  languages before this; what was missing was anything that read it, so
  choosing a language changed nothing on screen.

## Why a library

Hindi, Tamil, Telugu, Bengali and the rest do not pluralise the way
English does. `count === 1 ? "professional" : "professionals"` is
correct in English and wrong in most of the languages this app offers,
and wrong *silently* — nothing fails, the sentence is just malformed for
the reader. i18next resolves plurals through CLDR rules per language,
which is the part that is genuinely hard and easy to get wrong.

## Using it in a screen

```tsx
import { useTranslation } from "react-i18next";

export function SomeScreen() {
  const { t } = useTranslation();
  return <Text>{t("some.key")}</Text>;
}
```

Interpolation: `t("checkout.pay", { amount: "₹999.00" })` against
`pay: "Pay {{amount}}"`.

Plurals: define `thing_one` and `thing_other` in the catalogue and call
`t("thing", { count })`. Never branch on the count in the component.

Keys are `screen.element`, matching the screen's file name, so the string
for a piece of UI is findable from the component and vice versa.

## Language selection

`AuthContext` applies the signed-in user's `languagePreference` in one
place — it wraps `setUser`, so every path that sets a user keeps the
language in step and a future call site cannot forget. Signing out
resets to English rather than leaving the previous user's language on
the sign-in screen.

## Migration state

Migrated: RequestGuidance. Keys also exist for Checkout, Purchases,
Payment result, Today's Progress card and the More menu rows.

Everything else still carries inline strings. Those screens are not
broken — they simply do not translate yet. **New screens should use
`useTranslation()` from the start**; the retrofit gets more expensive
with every screen added, which is the whole reason this landed before
the remaining screens rather than after.

Only `en` is populated. The other nine languages resolve through
`fallbackLng`, so an untranslated screen shows English rather than a raw
key — showing `guidance.status.open.label` to a user is worse than
showing them a language they did not choose.

## Testing

`tests/i18n.test.ts` is valid vitest and **does not currently run**.
Installing a test runner into this workspace fails with an npm arborist
bug:

```
npm error Cannot read properties of null (reading 'edgesOut')
```

raised while resolving vitest 4's optional peers. It reproduces whether
vitest is declared in this workspace, pinned to an exact version, or
hoisted to the workspace root. `apps/api`'s copy lives under
`apps/api/node_modules` and is not hoisted, so it cannot be borrowed.

Every assertion in that file was verified by running the same checks
through `tsx` directly — plain keys, interpolation, both plural forms,
the fallback for an untranslated language, an unsupported language code,
and a scan for empty strings. All passed. But the file is not covered by
CI today, and a green build should not be read as covering it.

Fixing this is worth doing: it is the only workspace with no way to
assert anything, and the i18n layer is precisely the kind of code that
fails silently.
