# Open Questions & Gaps — Mobile App

Read alongside [../09-open-questions-gaps.md](../admin/07-open-questions-gaps.md) (the admin console's gap list) — several issues there (no auth-adjacent screens fully speced, no empty/loading/error states, no published design tokens) apply here too and aren't repeated in full below.

## 1. Two overlapping device-connection flows
"Health Connect Settings" (in Settings) and the "Connected Devices Hub" (in Recover) both manage wearable device connections, with overlapping UI (device cards, sync status, pairing). **Decision needed:** are these the same feature reachable from two entry points (fine, just needs consistent state), or two different concepts (e.g. one for platform-level HealthKit/Google-Fit permissions, one for individual Bluetooth devices)? Not resolvable from the static screens alone.

## 2. Subscription tiers vs. one-off program purchases — pricing model unclear
As noted in [01-product-requirements.md](01-product-requirements.md) §5, the app has both a 3-tier subscription (Basic/Pro/Elite) *and* an independent per-program purchase flow with its own AI-only vs. AI+Coach pricing. It's not clear from the design whether: (a) programs are sold only to non-subscribers, (b) subscribers get programs included and the purchase flow is for extras, or (c) these are fully independent revenue streams. This is a product/pricing decision that materially affects the commerce data model — see [06-cross-app-integration.md](06-cross-app-integration.md) §2.

## 3. Accent color is user-customizable — but the two apps don't share a palette
The Preferences screen lets a user pick an accent color (sample: Green/Yellow/Red), and the app's default accent (blue) differs from the admin console's default accent (mint green). **Decision needed:** should the mobile app's default accent be brought in line with the admin/brand green, with user-customization layered on top, or are "consumer app" and "operator console" intentionally allowed to diverge? Affects the shared `packages/ui` token set in [../07-project-structure.md](../platform/project-structure.md).

## 4. Timeline module's premium gating isn't explicit
Timeline screens are tagged `premium-header` in the layer names, and the subscription feature-comparison table lists "Progress Tracking" as Advanced-only on Pro/Elite — but it's not stated whether Timeline specifically requires a paid tier, or just enhanced Progress features do. Needs product confirmation before gating logic is built. **Update (19 Aug 2026):** Timeline (§G) is now built (`apps/api/src/modules/timeline`, `apps/user-mobile/src/screens/timeline/`) — deliberately left ungated for every subscription tier rather than guessing at this gap, since building the wrong gate would be worse than building none. Add the tier check once this is resolved.

## 5. Onboarding collects health/injury data with no visible consent/privacy screen in that flow
The Setup: Safety step (medical conditions, injuries) collects sensitive health information during onboarding, before any Terms/Privacy screen is shown again post-signup — the only consent checkbox seen is on the Login/Register screen ("I agree to Terms & Privacy Policy"), before this health data is even collected. **Recommend** an explicit, scoped consent moment for health-data collection specifically (separate from general ToS acceptance), consistent with how the admin console gates "Sensitive Health Metrics" behind an explicit access request (see [../09-open-questions-gaps.md](../admin/07-open-questions-gaps.md)).

## 6. "Acoustic Sleep Coach Voice" AI feature has no corresponding screen
The admin console's AI Feature Management Console lists this as a shipped/beta AI feature, but no dedicated sleep-coaching UI was found among the 82 mobile screens reviewed. Either it's delivered through an existing screen not obviously labeled for it (e.g. voice interaction bundled into the AI Coach chat) or its user-facing design hasn't been done yet — worth confirming with design before scoping AI Operations work for it.

## 7. iOS-only design — Android and tablet strategy undefined
All 82 frames are iOS-styled (status bar, home indicator) at a single phone size. If Android is in scope for launch, none of its platform conventions (back button, Material-style components) have been designed yet — this is a significant scope item to flag early, not a late-stage detail.

## 8. Multi-device "sessions" in Security settings implies more surfaces than reviewed
The Security screen's active-sessions list shows phone/laptop/tablet icons, implying a web or desktop client may exist or be planned — but no such client was found in either Figma file reviewed for this project. **Action needed:** confirm whether this is forward-looking design (a web app is planned but not yet designed) or should be scoped down to phone-only sessions for now.

## 9. Phase 0/1 built email+password auth, not the Figma-specified phone+OTP flow — **decided 20 Aug 2026: staying email+password for launch**
§A's Login/Register screen is designed around a phone number + OTP flow (+91 default, "Get OTP" CTA, a separate OTP Verification screen) — not email/password. The `apps/api`/`apps/user-mobile` scaffold (Phase 0/1) implemented email+password instead, because OTP delivery needs a third-party SMS provider (e.g. Twilio, MSG91) that hasn't been chosen, and building a fake/no-op OTP screen would be worse than flagging the gap. **20 Aug 2026 update:** this is now a closed decision, not an open one — email+password ships as the real launch auth, phone+OTP is explicitly deferred, not planned before MVP (see gap §38 and `docs/platform/mvp-launch-plan.md` §3). `apps/user-mobile/src/screens/auth/{LoginScreen,SignupScreen}.tsx` and `apps/api/src/modules/auth/` remain an intentional, sanctioned deviation from the reviewed Figma design, not an unresolved gap. If a later phase wants phone+OTP as an *additional* sign-in option, that's still real, buildable work — an SMS/OTP provider would need to be chosen — but it no longer blocks anything else.

## 10. Nutrition Dashboard's calorie/macro ring has no real goal to measure against
§D's Nutrition Dashboard shows "a calorie ring (consumed of goal)" and macro bars, but no screen or data field anywhere sets that goal — there's no calorie/macro target field on `User` or `OnboardingProfile`, and no goal-setting screen in the 82-screen inventory. The Phase 1 build (`apps/user-mobile/src/screens/fuel/FuelScreen.tsx`) uses a hardcoded placeholder target (2000 kcal / 150g protein / 200g carbs / 65g fat for every user) so the ring/bars have something to render against — this is clearly wrong for any real user and must not be mistaken for a real feature. **Decision needed:** either a BMR/TDEE calculation derived from onboarding data (weight/height/goals/training level already collected) or an explicit manual goal-entry screen — then wire it to replace `DAILY_TARGETS` in that file.

## 11. Accent color selection persists but doesn't re-theme the app
The Preferences screen (§N, pulled forward into Phase 1) lets a user pick and save an accent color via `PATCH /users/me` — the choice is correctly stored on `User.accentColor` and round-trips on reload. But `apps/user-mobile/src/theme/tokens.ts` exports `colors` as a static, module-level constant, not a context/provider — so nothing in the app actually re-renders in the chosen color yet. This is a known, intentionally-scoped gap (see the code comment in `PreferencesScreen.tsx`), not a bug: closing it means converting `tokens.ts` into a `ThemeProvider` that every themed component reads from, which is a broader refactor than this pass. Related to gap §3 (the two apps' default-accent mismatch) but distinct — that one is a product decision, this one is an implementation gap on top of whatever's decided.

## 12. Personal Records are "heaviest logged set," not a calculated 1RM
§F's Progress Overview lists "a personal-records list (trophy icon)". The Phase 2 build (`apps/api/src/modules/progress/progress.service.ts`) computes this from real `ExerciseSetLog` data — the heaviest `weightKg` ever logged per exercise, with the rep count and date it happened — rather than an estimated one-rep-max via a formula like Epley (`weight × (1 + reps/30)`) or Brzycki. This is an honest, real number from data the user actually produced, but it understates true strength for anyone who trains at higher reps and never tests a true heavy single — e.g. someone who only ever does sets of 10 will never show a PR near their real 1RM. **Decision needed:** keep "heaviest set" as the definition (simplest, least assumption-laden) or switch to an estimated-1RM formula (more standard in fitness apps, but introduces an estimate presented as fact). Either way, `PersonalRecord` in `packages/types` and the UI copy on `ProgressOverviewScreen.tsx` should make the definition explicit to the user.

## 13. Recovery & Devices remains blocked on infrastructure; AI Coach and Timeline are resolved
Phase 2 (`docs/platform/roadmap.md`) covers §E Recovery & Devices, §F Progress & Body, §G Timeline, and §H AI Coach. Progress & Body's core shipped 19 Aug 2026, Timeline shipped 19 Aug 2026 (a real read-only feed auto-generated from existing `WorkoutSession`/`ExerciseSetLog`/`Program` events, exactly the build-time-not-infrastructure item this entry originally flagged as worth prioritizing next), and **AI Coach shipped for real 25 Aug 2026** (`apps/api/src/modules/aiCoach`, `apps/user-mobile/src/screens/recover/AiCoachScreen.tsx`) — genuine conversation persistence, prompt design grounded in the user's real goals/workouts/measurements, per-user rate limiting, and a bounded per-turn history cost, closing the LLM-provider-decision blocker this entry originally raised (the `AI_PROVIDER`/API-key plumbing landed 20 Aug 2026; nothing called it until now). **Recovery & Devices' device-pairing half is the one item still genuinely blocked**, and stays that way for the same reason as always: it needs real Bluetooth/HealthKit/Google Fit integration against physical hardware and Apple/Google developer accounts, and no honest mock data source exists to build against — a fake device list or recovery score would misrepresent hardware this app has no way to actually talk to. That's a product/infrastructure decision only the user can make (which wearables to support, developer account enrollment), not something buildable in this environment.

**Update, 31 Aug 2026 (not reflected above — the paragraph is left as-written):** the Recovery Dashboard screen itself is no longer blocked, only the four device-pairing screens (Connected Devices Hub, Add Device, Device Pairing, Sync Dashboard) are. `apps/user-mobile/src/screens/recover/RecoveryScreen.tsx` ships a real manual-entry stopgap — resting heart rate, sleep, HRV, soreness, and energy, self-reported rather than device-synced — wired into `RecoverStack` as a real route, not a placeholder. `docs/platform/roadmap.md`'s 31 Aug batch summary lists this alongside the same batch's other real shipments; its own Phase 2 §E section further down was never updated to match, same doc-drift as this entry.

## 14. No payment gateway wired up — Subscribe / Purchase Program activate directly, no card entry or charge
§M's Subscription Plans/Management screens (`apps/user-mobile/src/screens/more/SubscriptionScreen.tsx`) let a user subscribe, switch, or cancel a plan against a real `Subscription`/`SubscriptionPlan` backend (`apps/api/src/modules/subscriptions`), and §I's Program Purchase (`apps/user-mobile/src/screens/train/ProgramDetailScreen.tsx`/`WorkoutDetailScreen.tsx`) lets a user buy a priced program against a real `ProgramPurchase` backend (`apps/api/src/modules/programPurchases`) — but there's no payment gateway (Stripe, Razorpay, or similar) integrated anywhere in the stack. `POST /subscriptions` and `POST /programs/:id/purchase` both activate immediately, server-side, with no card-entry step and no charge — which means the Figma-specified Payment Checkout / Payment Success / Payment Failed screens were deliberately not built for either flow, since building them without a real gateway behind them would show a fake card form that implies money is changing hands when it isn't. Switching subscription plans while one is already active/trialing also has no proration logic — the old subscription is simply marked `canceled` and a new one starts immediately at full price; program purchases are one-off and don't have this issue. **Decision needed:** pick a payment gateway (Stripe and Razorpay are the common choices for a business with both US- and India-style billing needs) before either checkout flow can be built for real, and decide whether subscription plan switches should be prorated. Until resolved, `apps/user-mobile/src/screens/more/SubscriptionScreen.tsx`, `apps/user-mobile/src/screens/train/{ProgramDetailScreen,WorkoutDetailScreen}.tsx`, and their backend modules do not match the reviewed design's checkout flow.

## 15. Program Purchase is single-tier — no AI-only vs AI+Coach add-on choice
§I's Program Purchase screen is designed around a plan choice at checkout — **AI Program** vs **AI + Coach**, priced independently (e.g. ₹1,299 vs ₹1,799 in the sampled screen, see [01-product-requirements.md](01-product-requirements.md) §5). The Phase 3 build (`apps/api/src/modules/programPurchases`) only supports a single price — `Program.priceCents`, the same field already shown on Train Dashboard/Program Detail — with no add-on tier, because "AI + Coach" implies a human coach gets assigned to that purchase, and the Coach/CoachBooking entities that would represent that don't exist until Phase 5 (see [06-cross-app-integration.md](06-cross-app-integration.md) §2). Building a selectable-but-inert "AI + Coach" option now would misrepresent it as functional. This is related to but distinct from gap §2 (whether program access and subscription tier stack) — that one is about *whether* purchase is even the right gate, this one is about the *missing second tier* of an already-real purchase flow. **Decision needed:** once Phase 5's Coach marketplace exists, add a second `priceCents`-equivalent field (or a separate `ProgramPurchaseTier` enum) and wire "AI + Coach" purchases to actually assign a coach.

## 16. Reminders are purely local, on-device notifications — no server-push, no custom sounds
§K's Reminders (`apps/api/src/modules/reminders`, `apps/user-mobile/src/screens/more/{RemindersScreen,ReminderFormScreen}.tsx`) shipped 19 Aug 2026 as real, working local notifications via `expo-notifications` — creating/editing/deleting a reminder genuinely schedules/reschedules an on-device iOS notification (`apps/user-mobile/src/lib/reminderNotifications.ts`, full cancel-and-reschedule sync on every list load and every mutation). Two simplifications are worth flagging explicitly rather than leaving implicit: (1) there is no server-push infrastructure anywhere in this app (no APNs/FCM wiring, no push-token storage) — the server only stores *what* to schedule; all actual delivery happens locally, which means a reminder won't fire if the app has been force-quit long enough for iOS to have reason to not relaunch it for a local notification (in practice local notifications scheduled this way persist across normal backgrounding, this is only a concern for aggressive force-quit + long idle scenarios); (2) the "alarm-sound toggle" in the design is only ever a **default-sound on/off** switch — there's no bundled custom audio asset and no sound picker, since no sound files were provided as part of this design pass. Neither is a build shortfall so much as a scope boundary of "local reminders only" — building real push would need the same kind of provider decision (APNs cert/FCM project) as gap §14's payment gateway or §13's AI Coach LLM provider, so it was deliberately kept out of this slice rather than half-wired.

## 17. Security screen: two-factor authentication is real now (25 Aug 2026); two build-time simplifications remain on what shipped earlier
§L's Security screen (`apps/api/src/modules/users`, `apps/user-mobile/src/screens/more/SecurityScreen.tsx`) shipped 19 Aug 2026 with real password change (revokes every active session, forcing re-login everywhere — a deliberate security behavior, not a bug), a real active-sessions list with per-session revoke, a real GDPR-style "download my data" export, and real account deletion (cascading hard delete, password-confirmed). **Update (19 Aug 2026):** biometric login also now real — see gap §22, which supersedes the earlier "deferred for scope" note that used to live here.

**25 Aug 2026: two-factor authentication shipped for real**, closing this gap's original blocker — but not the way this entry originally framed it. The old text lumped "SMS/TOTP" together as one blocker needing one provider decision; that conflated two genuinely different things. SMS-based 2FA does need a third-party gateway account (Twilio/MSG91-style — the same real blocker as gap §9's phone+OTP). TOTP-based 2FA (the authenticator-app codes Google Authenticator/Authy/1Password produce — RFC 6238) needs no external account or business decision at all: it's pure cryptography against a shared secret, verified entirely server-side. That's what actually shipped — `apps/api/src/lib/twoFactor.ts` (secret generation, QR rendering, code verification, AES-256-GCM encryption of the stored secret via a new required `TWO_FACTOR_ENCRYPTION_KEY` env var — this app generates that value itself, unlike a provider API key), `apps/api/src/modules/users`' setup/enable/disable endpoints, a login-flow change (`POST /auth/login` now returns a short-lived challenge token instead of real tokens when 2FA is on; `POST /auth/2fa/verify` completes it), and mobile UI for both enrollment (QR scan → code confirm → one-time recovery codes) and the login-time challenge screen. Genuinely different from Biometric Unlock: 2FA gates login itself against a second real-world factor (something the user's phone's authenticator app knows), where Biometric Unlock just re-locks an already-signed-in session locally — see gap §22.

Two build-time simplifications remain on what shipped earlier: **Active Sessions** is real (list + per-session revoke, backed by `RefreshToken`) but confirms gap §8's concern in code — there's no device metadata captured at login, so sessions list plainly by issue/expiry date rather than with the phone/laptop/tablet icons the design shows; and **Download My Data** shares the export as JSON text via React Native's native `Share` sheet rather than saving a downloadable file, since no file-export library (`expo-file-system`/`expo-sharing`) is wired up yet.

## 18. Notification category-level toggles and Data & Privacy's data-sharing toggles aren't built — no real pipeline for either to gate yet
§L's Notification Settings screen (`apps/user-mobile/src/screens/more/NotificationSettingsScreen.tsx`) ships with exactly one real control: a master on/off switch (`User.notificationsEnabled`) that gates whether the client schedules any local Reminder notification at all. The design's broader "at least 6 individually-toggleable categories and two advanced rows" aren't built as a second, parallel toggle system — category-level control over notifications already lives for real on the Reminders screen itself (each Reminder has its own category and `isEnabled`), and there's no push infrastructure (gap §16) for the design's likely intent of broader categories like achievement alerts or weekly summaries, which would need server-push to mean anything. Separately, the design's "Data & Privacy" screen also specifies data-sharing toggles (the GDPR-adjacent download/delete actions from that same screen were built for real — see gap §18 — but the sharing toggles were not); there's no analytics pipeline, no health-data-sharing-with-a-future-Coach pipeline, or any other real destination for a "share my data" preference to control yet, so building inert toggles now would misrepresent them as functional. **Decision needed:** define what "data sharing" should actually mean and gate in this app — for example, an analytics opt-out once any analytics pipeline exists, or a workout/health-data-sharing consent once Phase 5's Coach marketplace can actually consume it — before building real toggles for either.

## 21. Sandbox infrastructure note: Expo's own package-resolution API is blocked in this build environment
Separate from the pre-existing `binaries.prisma.sh` block documented in `apps/api/README.md`, this build environment also cannot reach Expo's own SDK-compatible-version resolution endpoint — `npx expo install <package>` fails outright (`SyntaxError: ... "Host not i"... is not valid JSON`, i.e. it receives an HTML/text error page where it expects JSON). This surfaced adding `expo-notifications` for Reminders, again adding `expo-clipboard` for Referral, and a third time adding `expo-local-authentication` for Biometric Unlock. **Workaround used, and reusable for any future Expo-managed package:** query npm's registry directly — `npm view <package> versions --json`, then read the package's `dist-tags` object for the `sdk-<N>` tag matching this project's Expo SDK (51) — and `npm install <package>@<exact-version> --workspace=<app> --save-exact`, then hand-edit `package.json` to a `~`-range matching the convention of the app's other `expo-*` dependencies. This is an environment limitation of the sandbox this was built in, not a real dependency conflict — `npx expo install --check` should be re-run once on a machine with normal network access to confirm versions are still aligned.

## 22. Biometric Unlock is a real app-lock, not a second login path — and now has a real, configurable idle timeout (20 Aug 2026)
§L Security's **Biometric Unlock** toggle (`apps/user-mobile/src/lib/biometricAuth.ts`, `AuthContext.tsx`, `screens/lock/LockScreen.tsx`) shipped 19 Aug 2026 via `expo-local-authentication`, superseding the "deferred for scope" note that used to live in gap §17. It's real: turning it on requires passing a live Face ID/Touch ID challenge first (so a user can't enable a setting that silently doesn't work), the flag persists per-device in `expo-secure-store` (deliberately not a `User` field — hardware/enrollment is a property of the device, not the account, so it doesn't sync across a user's other devices), and `RootNavigator` gates `MainTabs` behind a real `LockScreen` challenge whenever it's on. Two things worth being explicit about: (1) this is an **app-lock**, not a second authentication factor on top of login — the access/refresh tokens are already sitting in secure storage exactly as they are for any returning user, so passing the Face ID challenge just clears a local UI gate, it doesn't re-authenticate against the server (that's what two-factor auth, gap §17, would do instead, and remains unbuilt); (2) **20 Aug 2026 update:** re-locking now has a real, configurable idle timeout, closing the gap this note used to flag. `SecurityScreen`'s Biometric Unlock card gained a Chip row ("Immediately" / 1 / 5 / 15 / 30 min, shown only while the toggle is on), persisted per-device via the same `expo-secure-store` mechanism as the on/off flag itself (`biometricAuth.ts`'s `getBiometricLockIdleTimeoutMinutes`/`setBiometricLockIdleTimeoutMinutes`). The implementation had to solve a real constraint: there's no way to run a JS countdown timer while iOS/Android has suspended a backgrounded app, so `AuthContext.tsx`'s `AppState` listener now records a timestamp the instant the app leaves `active` and, the instant it returns, compares elapsed time against the stored threshold — the same after-the-fact approach real password-manager apps use, rather than a live countdown. "Immediately" (0 minutes) is the default for any device that's never touched this setting, which makes it reproduce the exact pre-20-Aug-2026 always-lock-on-background behavior byte-for-byte — this is a strictly additive change, nothing about the existing default lock behavior shifted underneath anyone. Logging out and back in within the same foreground app session still doesn't re-trigger a challenge, since nothing backgrounds the app in that flow — that part of the original note still stands, and isn't a blocker on any product decision either.

## 23. Error/empty states use a shared component + real Retry, and now a real offline banner + auto-retry — only the toast/snackbar system remains out of scope (20 Aug 2026)
The cross-cutting "empty/loading/error states per screen" item in `docs/platform/roadmap.md` (flagged there as unbuilt since neither Figma file specifies these) was picked up 19 Aug 2026 as a genuinely unblocked slice: two shared components (`apps/user-mobile/src/components/ErrorState.tsx`, `EmptyState.tsx`) and a shared `src/lib/apiError.ts` (`extractErrorMessage`, generalized from what only Security's screen had before) are now wired into all 21 screens that read from the network — every one gets a real `isError` branch with a Retry button bound to React Query's own `refetch`, not a decorative one — and into every mutation call site that writes data (purchase, subscribe/cancel, log a meal/set/measurement, toggle a reminder, save a profile/preference field, submit onboarding, change password, revoke a session, export data, and more), each of which now shows a real `Alert.alert` on failure instead of silently re-enabling its button with no explanation. Of the three things this originally left out, two are now real (20 Aug 2026): (1) **a real offline/no-connection banner** — a new `OfflineBanner.tsx`, backed by `@react-native-community/netinfo` (newly a dependency), mounted once in `App.tsx` above/around `RootNavigator` so it's visible regardless of auth/onboarding/lock state. It reads `state.isConnected === false`, deliberately not `!state.isInternetReachable` — `isInternetReachable` starts out `null` until NetInfo's periodic reachability probe resolves, so treating "not yet known" as offline would flash the banner on every cold start even on a good connection. ## 37. The app now genuinely renders in this sandbox — a real web export was added purely as a dev-preview aid, NOT as a new supported product platform

## 38. Real Razorpay payment integration and AI provider config landed 20 Aug 2026 — closing gap §14 for real, and resolving two of `mvp-launch-plan.md`'s open decisions (phone+OTP deferred, payment gateway chosen)
Three decisions from `docs/platform/mvp-launch-plan.md` §3 landed together 20 Aug 2026: **Razorpay** is the chosen payment gateway, **AI key configuration** (infrastructure only) is real, and **phone+OTP auth is explicitly deferred** — email+password remains the launch auth, not a placeholder pending a provider decision (see gap §9, updated to reflect this).

**Razorpay (closes gap §14 for real).** `apps/api/src/modules/payments` adds a real order/verify/webhook flow, shared by both Subscription & Payments (§M) and Programs Commerce (§I) rather than duplicating payment logic per feature: `POST /payments/razorpay/orders` resolves the real server-side price (never trusts a client-supplied amount) and creates a Razorpay Order; the mobile client opens Razorpay's hosted Checkout inside a `WebView` (`RazorpayCheckoutModal.tsx`) and calls `POST /payments/razorpay/verify`, which recomputes the HMAC signature server-side — that recomputation is the actual security boundary, not the client reporting success; `POST /payments/razorpay/webhook` is a second, independent path to the same activation logic, so a payment that succeeds but whose client crashes before calling `/verify` still gets recorded and still grants access. A new `Payment` model is the durable record of every attempt. `subscribe()`/`purchaseProgram()` (the same functions the old direct-activate flow used) now both require a `verifiedPayment: true` option for any non-free plan/program — set only by the payments module after a real verification, so calling either service function (or the pre-existing, still-registered `POST /subscriptions`/`POST /programs/:id/purchase` routes) directly for a paid item now correctly 402s instead of activating for free. Four things worth being explicit about: (1) **no native Razorpay SDK is linked** — that needs native module linking (a custom dev client / EAS build, not this app's plain managed workflow, same class of constraint as gap §21) — so checkout uses a `WebView` loading Razorpay's own hosted `checkout.js`, a real, working integration pattern, just not the native-SDK one; (2) **this build environment has no real Razorpay merchant credentials** — `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` are all optional env vars (`.env.example`), and every payment route 503s cleanly with `payment_gateway_not_configured` when they're unset, rather than crashing — real test-mode keys from a real Razorpay dashboard are needed before this can be exercised end to end; (3) **a real, unresolved currency mismatch**: every seeded `priceCents` value in this app was chosen and is displayed as USD cents (`$14.99` on Subscription, `$X.XX` on Program Detail), but Razorpay's native currency is INR (`RAZORPAY_CURRENCY` defaults to `"INR"`), and passing those same integers through as-is would functionally undercharge by roughly 80x (₹14.99 instead of a real ~₹1,200). This needs either real INR list prices seeded, or a Razorpay account specifically configured for international/USD settlement, before real money should flow through it — this pass deliberately did not silently pick one; (4) **`react-native-webview` has no web implementation** (confirmed via the sandbox's own web-preview export, gap §37 — it renders fine at launch since the WebView is never mounted until a purchase button is tapped, but would fail if one were), so the Razorpay checkout flow specifically is native-only (iOS/Android) — consistent with gap §37's own point that the web preview is a dev-verification aid, not a real target platform, so this isn't a new gap so much as an expected consequence of that one.

**AI key configuration (gap §13's infrastructure half only).** `apps/api/src/lib/aiClient.ts` adds provider-agnostic config (`AI_PROVIDER` env var, `anthropic`/`openai`, plus the matching API key) and a thin `generateCompletion()` wrapper using the platform's native `fetch`, plus a `GET /ai/status` endpoint to confirm what's configured without exposing the key. **This is deliberately just the plumbing, not the AI Coach feature** — nothing in this app calls `generateCompletion()` yet. Building AI Coach chat (or a workout generator, diet-log vision, readiness scoring) still needs conversation persistence, prompt design, streaming responses, rate limiting, and cost controls, none of which this pass attempted — gap §13/§H stay open for that. Like Razorpay, both provider keys are optional and unset in this environment; `isAiConfigured()` returns `false` until a real key is supplied.

**Phone+OTP: decided, not just deferred.** Gap §9 previously read as an open question ("needs an SMS-provider decision to close"). It's now a closed decision for MVP: email+password ships as the launch auth, phone+OTP is out of scope for v1. If a future phase wants phone+OTP as an *additional* sign-in option (not a replacement), that's still real, buildable work — an SMS/OTP provider (Twilio or similar) would need to be chosen and wired up — but it's no longer blocking anything else in this plan.
